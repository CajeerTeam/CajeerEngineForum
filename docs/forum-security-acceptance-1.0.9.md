# Forum Edition 1.0.9 — Security & Integration Acceptance

Версия ядра остаётся **CajeerEngine 2.1.0**; изменяется только Forum Edition (`release.json:edition_version`). Это обновление исполняемых PHP-обработчиков и миграционного раннера, **новых SQL-миграций нет**. Перед обновлением — резервная копия файлов, БД и отдельная проверка возможности восстановления.

## Изменения безопасности

- `/forum/account/security` теперь завершает TOTP-активацию через существующий `TwoFactorTotp::matchingStep()` и атомарно сохраняет последний использованный шаг в `ce_users.two_factor_last_step`. Повторное предъявление той же TOTP не подтверждает новую сессию, вход или новое привилегированное действие. Recovery-коды остаются одноразовыми.
- Тот же CAS шага применяется при локальном входе и при повторном подтверждении доступа. Изменение статуса 2FA отклоняется, если текущая SkiF4er ID-сессия не прошла подтверждённый OIDC MFA step-up; передача локального пароля в API не заменяет это доказательство. При ошибке чтения реестра доступ не повышается.
- `migrate:repair` **отказывается** автоматически удалять failed-маркер MySQL/MariaDB: DDL там может неявно завершать транзакции, поэтому повторный запуск опасен. До восстановления в исходную схему по проверенному бэкапу не изменяйте SQL и не удаляйте failure-маркеры вручную. Для SQLite/PostgreSQL файл сбойной миграции должен совпадать с записанной контрольной суммой.
- Проверка реестра сессий обнаруживает осиротевшие строки даже при ошибочно отключённых внешних ключах во время восстановления БД.

## Регрессионные проверки

```bash
php tools/forum-security-acceptance-regression.php
php tools/forum-totp-109-regression.php
php tools/forum-mysql-repair-109-regression.php
php tools/forum-unified-access-regression.php
php tools/forum-identity-regression.php
python3 tools/forum-tests/security_109_sql_regression.py
php tools/identity-session-acceptance-integration.php --require-db
```

Последние две PHP-интеграционные команды требуют установленного `vendor`, `pdo_sqlite` и `mbstring`. SQLite-тест на Python действительно исполняет 77 исходных SQL-миграций на заполненной исторической базе и проверяет сохранность пользователей/тем/сообщений, целостность OIDC-связей, локальные сессии, одноразовый logout и избирательный отзыв. Он **не заменяет** PostgreSQL/MySQL и реальный SkiF4er ID.

## Проверка развернутой системы

```bash
composer install --no-dev --prefer-dist --no-interaction
php bin/cajeer migrate
php bin/cajeer identity:sessions:status
# Выполнять только после проверки резервной копии и завершения backfill:
php bin/cajeer identity:sessions:migrate --yes --batch-size=100 --max-batches=10
php tools/forum-security-acceptance.php --json
```

Последняя команда **только читает** данные и проверяет установленные файлы миграций, контрольные суммы, состояние session registry, минимальные права `forum-member`, целостность Identity, доступность IdP JWKS/discovery и доступность публичной HTTPS-площадки. Выход `0` означает прохождение этих программных проверок, `1` — отказ, `2` — отсутствие зависимостей/небезопасный режим проверки.

`--offline` допускается только вне production: он отключает сетевые запросы к IdP и сайту, но не отключает проверки БД и параметров OIDC. Production-проверка **всегда требует** настроенный confidential OIDC client и сетевые проверки. Не выводите client secret, PKCE verifier, access/id tokens или session cookies в отчёт.

## Необходимые ручные e2e-сценарии на staging

С отдельным тестовым пользователем, настоящим SkiF4er ID и HTTPS проверьте: существующий локальный и OIDC вход, первичную регистрацию (при разрешении), запрет автосвязывания по email, привязку и отвязку, актуальность ACL/санкций после изменения ролей, локальный/глобальный выход, отзыв устройства, MFA step-up, а также регистрацию/отклонение одного и того же TOTP-кода при повторе. Дополнительно проверьте миграцию и откат резервной копии на **каждом используемом** серверном драйвере БД.

Без реального IdP-клиента, зарегистрированных callback URL, staging-данных и журнала успешных CI/ручных проверок **нельзя считать production go-live завершённым**. `--json` не создаёт сертификат и не заменяет выполнение этих сценариев.
