## Главное в выпуске

Версия 1.6.0 завершает реализацию механизма допуска автоматизированных обновлений через GitHub. В центре внимания — не только установка новой версии, но и доказуемая идентичность пакета, проверка предыдущего релиза, сохранность данных и независимое подтверждение обновления после публикации.

| Изменение | Польза |
| --- | --- |
| Точная подписанная база 1.5.11 и кандидат 1.6.0 | Приёмка проверяет реальные версии и байты, а не подменённые номера |
| Независимые prepublication и postpublication проверки | Подтверждение работоспособности реального GitHub-пути до назначения Latest |
| Сверка run ID, попыток, commit и digest | Исключение смешивания доказательств разных сборок |
| Дополнительные проверки автономного допуска и minor-перехода | Контроль корректного перехода 1.5.11 → 1.6.0 |
| Повторная проверка опубликованного комплекта | Уже опубликованные архивы не перезаписываются |

## Что уже входит в ветку 1.5.x

Обнаружение GitHub Releases с ETag и cooldown; последовательное обновление и каналы; возобновляемая загрузка; окна обслуживания и блокировки; opt-in автономная установка; репетиция восстановления свежего backup; управление службами systemd; независимое восстановление после сбоя; ACP Update Center; Ed25519 trust policy, отзыв ключей, подписанная авторизация с ограниченным сроком и SBOM.

## Известные ограничения

- Автономный режим не включается автоматически. `automatic_patch` не допускает переход на 1.6.0.
- Поддержка автономного восстановления ограничена SQLite/PostgreSQL при совместимом локальном профиле; MySQL/MariaDB, внешнее хранилище и Redis-backed queue не входят в этот протокол.
- Истёкшая авторизация промежуточного релиза блокирует последовательное обновление. Повторно авторизуются те же байты; нельзя пересобирать опубликованную версию под прежним номером.
- Релиз, опубликованный без назначения `Latest`, уже публичен. Это не скрытый canary и не запрет установки для старых клиентов.
- Нет основания заявлять о пройденном 24-часовом soak, подписанной production-поставке или успешном обновлении реального хоста без независимых отчётов.

## Проверка идентичности сборки

В предоставленном исходном архиве `VERSION` содержит `1.6.0`, тогда как `release.json` задаёт `version` и `upstream_version` как `2.1.0`, а `edition_version` как `1.6.0`. `tools/release-freeze.py` требует равенства `VERSION` и версии ядра в `release.json`. Это блокирующее расхождение следует устранить в отдельном проверенном изменении исходников до квалификации. Документационный пакет не изменяет version-файлы, код или манифесты и не скрывает этот дефект.

## Критерии готовности к Latest

- [ ] Устранена и проверена идентичность исходников, существует подлинный `v1.5.11` в истории main.
- [ ] Успешны CI, SQL/queue/browser E2E и подписанное обновление/откат.
- [ ] Выполнены физические профили 10k/100k/1M и 24-часовой soak.
- [ ] Пройдены обе независимые Chaos-проверки `drained` и `activating`.
- [ ] Подтверждён реальный GitHub-переход 1.5.10 → 1.5.11.
- [ ] Подписанный комплект опубликован без Latest после prepublication gate.
- [ ] На отдельной VM подтверждён переход 1.5.11 → 1.6.0 с точным публичным dist.
- [ ] Повторный release gate проверил весь набор доказательств и назначил Latest.

Пункты — критерии допуска, а не отчёт о выполнении. См. [порядок квалификации](../forum-github-updates-stable-1.6.0.md).

## Артефакты поставки

В `release.json` указаны `cajeerengine-1.6.0-source.zip`, `cajeerengine-1.6.0-dist.zip`, SHA-256 sidecars и `cajeerengine-1.6.0-artifacts.json`. Полная публикация включает предусмотренные workflow подписи, манифесты и авторизацию. Фактическое наличие и содержимое удалённого релиза проверяет процедура публикации; документация не подтверждает, что он уже опубликован.
