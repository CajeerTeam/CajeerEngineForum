# Forum Edition 1.0.8 — Unified Access Control

## Что выполняется на сервере

- `AuthService::authenticateRequest()` сверяет полномочия токена с **актуальными** правами `ce_user_roles`, проверяет активный статус и санкции. Любые внешние OIDC-claims не создают локальных ролей.
- `ForumAccessPolicy` и `NodePermissionService` перепроверяют полномочия участника из БД; ACL категорий и досок рассчитываются `PermissionResolver`. Правило `never` у родителя исключает доступ к потомкам, а явно делегированная модерация не становится глобальной.
- Мутации Forum ACP, ACL, ролей, членства групп, ограничений, санкций, структуры сообщества и другие административные изменения защищены `AuthenticationAssurance::required()` **до вызова контроллера**. Рутинное чтение/публикация не требует step-up.
- Действительный `ce_session` и CSRF обязательны для step-up; внешние Bearer/API-токены не являются доказательством свежей браузерной аутентификации. Никакие значения `assured_at`, `user_id` и прав из тела запроса не принимаются.
- Для local/legacy сессии: текущий пароль + TOTP, если он включён; доказательство записывается в **текущую** `ce_user_sessions` с ограничением 60–900 сек (`AUTH_ASSURANCE_TTL_SECONDS`, по умолчанию 300), обновление не допускается для SkiF4er-сессии даже при гонке.
- Для SkiF4er-сессии: повторная авторизация Keycloak с `max_age=0`, подписанными `auth_time` и `amr` (MFA). Локальный пароль не заменяет эту проверку. Связывание `(issuer, sub)` и активность исходной сессии проверяются OIDC-сервисом ядра. После успешного callback `assured_at` записывается для исходной сессии.

## Поведение интерфейса

1. Авторизованный администратор/модератор открывает страницу форума или ACP и выполняет критичную операцию.
2. Если подтверждение устарело, сервер отвечает `403 step_up_required` **до изменения данных**. Проверки RBAC, ACL и действующих санкций при этом не ослабляются.
3. Local: UI просит локальный пароль/TOTP, вызывает `POST /api/v1/auth/assurance/confirm` с CSRF и повторяет **только отвергнутый** запрос **один раз**.
4. SkiF4er ID: UI вызывает `POST /api/v1/identity/step-up/start` с `return_to` (относительный `/forum/...`). Сервер подписывает адрес на случайной cookie транзакции, а после подтверждённого OIDC MFA возвращает на ту же страницу. Мутация не повторяется автоматически после навигации — пользователь сознательно повторяет действие.
5. Если IdP недоступен, MFA не подтверждено, сессия отозвана/ротирована, истёк срок или `return_to` подменён — операция остаётся отклонённой.

## Обновление

Новых миграций не требуется: используются `ce_user_sessions` и хранилище OIDC транзакций CajeerEngine 2.1.0. Перед включением строгих правил убедитесь, что выполнена миграция legacy-сессий ядра и OIDC клиент поддерживает MFA и корректный `auth_time`/`amr`. Проверьте реальный вход, обратный callback и настройку proxy TLS на staging.

## Регрессии и ограничения

```bash
php tools/forum-unified-access-regression.php
php tools/forum-unified-access-oidc-regression.php
node tools/forum-unified-access-browser-regression.mjs
php tools/oidc-regression.php
php tools/forum-ski-id-login-regression.php
```

Изолированные тесты выполняют реальный PHP/JS код с контролируемой сессией/IdP, но **не заменяют** полное HTTP-тестирование с реальной PostgreSQL/Keycloak и Composer зависимостями на staging. Не называйте эту сборку сертифицированной без результатов полного CI и реальной проверки.
