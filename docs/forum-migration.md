## Version 1.1.5 — XenForo conversations and media (pipeline v5)

New XenForo import jobs use a 20-phase pipeline. After the v4 phases, the importer copies active private conversation recipients, messages, private attachment bytes, and finally rewrites safe local links/BBCode. Old v1-v4 jobs continue on their recorded sequence and do not change their checkpoints. It is unsafe to manually edit `plan_json` or reuse a snapshot label for different source data.

Use an immutable XenForo 2.2/2.3 database snapshot with `xf_conversation_master`, `xf_conversation_recipient` and `xf_conversation_message`, plus `--files=/absolute/path/to/internal_data/attachments` for the actual original file bytes and `--avatar-files=/absolute/path/to/data/avatars` for avatars. `forum:import:plan` fails on an unsupported or missing conversation table/column; `forum:import:run` will not create a new recovery backup when required files or avatars have not been provided. Attachment keys follow the version-specific `file_key`/`file_hash` behavior from v1.1.2. Empty, deleted or incomplete recipient sets are explicitly skipped, not exposed to a new audience; copied user accounts remain disabled pending operator verification. Unsupported, oversize, missing or unsafe files are recorded as skipped with precise reasons. Import only from a complete backup under exclusive maintenance; do not place the snapshot under a public web root.

The target conversation tables are **not** tied to a hidden forum category. Newly imported users stay `disabled` and must not be activated before the import has completed and recipient privacy has been manually audited. Original message dates and author identities are retained when available; vanished authors are represented as nullable authors rather than being incorrectly reassigned. New recipients are never generated by matching source email addresses. Download of a private attachment requires the same server-side conversation membership checks as a normal Forum attachment. Public legacy redirects only cover visible, authorized thread/board/post content; historical private conversation IDs are not exposed through the public legacy redirect service. Before production cutover, reconcile the import job map and run an actual authenticated + guest download ACL check on staging.

## Version 1.1.4 — XenForo community data (new pipeline v4)

New XenForo jobs use **16 phases**: the original eleven, `profiles`, `reactions`, `avatars`, `follows`, `content_links`. Existing jobs (v1: 11, v2: 13, v3: 14 phases) remain unchanged. Never rewrite an active job ledger.

Use a **frozen, read-only** source DB snapshot. For profiles with uploaded avatars, copy the complete XenForo `data/avatars` directory to a local, immutable directory and supply `--avatar-files=/path/to/frozen/data/avatars` for **both plan and run**. `--files` still points to the separate XenForo attachment-data snapshot and is not a substitute. The normal original path is `o/<user_id divided by 1000>/<user_id>.jpg`, falling back to `l/...` if the original is absent. Missing, corrupt, oversized, or unsafe avatar files are explicitly skipped with a reason; an avatar source with rows but no `--avatar-files` **cannot start**. GD is required for safe resampling and JPEG metadata stripping. The resulting JPEG is stored in `ce_forum_profile_images` and served via the existing access-controlled profile endpoint.

The engine validates `xf_user.avatar_date`, `xf_user_follow(user_id,follow_user_id)`, and an immutable schema hash for newly created jobs. It imports mapped `follow` relationships to `ce_forum_member_relations`, preserving private profile preferences, and never creates relationships for users omitted due to identity conflicts. Source primary groups become **display primary** for new jobs only, while original group permissions remain `[]`. Existing imported thread/board watches and standard reactions remain supported. Administrator and moderator rights are **never inherited** from XenForo group labels; review mapping and manually approve before publishing the hidden/readonly imported tree.

Run `php tools/forum-xenforo-community-unit.php` for a driver-free validation, and `php tools/forum-xenforo-community-integration.php` with PHP 8.4, PDO SQLite, GD and the migrated target schema to check rollback and restart. Run the same with source MySQL/MariaDB and target PostgreSQL in staging before cutover. These fixture tests do not certify any real third-party backup.

## Version 1.1.3 — XenForo content fidelity (new pipeline v3 only)

New XenForo 2.2/2.3 jobs record `pipeline_version=3` and `content_links` source counts/high-water mark in `ce_forum_import_jobs.plan_json`. Phases 0–12 remain unchanged; new phase 13 rereads **the same immutable source posts** after all users, threads, messages and attachments have been mapped. It converts supported native BBCode and rewrites referenced IDs in place. A converted post, original revision, `content_links` outcome and cursor commit in **one target DB transaction**. An interrupted run restarts from the committed keyset. No new SQL migration is required.

**Old jobs stay old:** v1 jobs retain 11 phases; jobs created with 1.1.1/1.1.2 retain 13 phases (v2) and are neither reinterpreted nor silently upgraded. In-flight plans must not be edited. If you want converted historical content in a v2 job, complete it and plan a fresh import from a new frozen snapshot into a separately prepared target; do not reuse the previous backup or job ID.

For rewriting *absolute* links to the old XenForo site, set the optional source URL origin once in the environment before plan/import, e.g. `FORUM_IMPORT_SOURCE_ORIGIN=https://archive.example/community`. It must match the exact original HTTP(S) scheme, host, port and installation path; there are no wildcard matches. The origin is in the job identity and frozen plan. **Keep it unchanged when resuming.** Without this variable, relative XenForo URLs such as `/threads/topic.123/` and `/posts/456/` are still resolved, while absolute links are treated as ordinary external links (do not automatically assume a third-party host is the source). Posts referring to a deleted, private or skipped object will keep an inert text label, never a redirect to an unreviewed old private target.

Implemented: safe `[B]`, `[I]`, `[U]`, `[S]`, `[QUOTE=... post: N]`, `[USER=N]`, `[CODE]`, lists, headings, `[URL]`, local attachment download links, and bare source URLs outside `[URL]` blocks; converted bodies are stored as BBCode and rendered through `ForumContentRenderer` (HTML-escaped and URL-allowlisted). No historical notification or mention event is emitted. Images become ordinary safe clickable links; remote images are **not downloaded or embedded**. Unsupported add-on tags remain inert source text, not executable HTML. Posts exceeding renderer limits are explicitly skipped from the initial import; conversions that would exceed the limit remain in safe plain form with a `content_links` skip reason. Review these skips prior to cutover.

Local tests: `php tools/forum-xenforo-content-regression.php` and `python tools/forum-tests/xenforo_content_sql_regression.py` require no PHP database driver; `php tools/forum-xenforo-content-integration.php` requires PDO SQLite/mbstring and runs the actual importer, injected write failure, rollback and restart. For production, test actual immutable XenForo 2.2/2.3 snapshots and real PostgreSQL/MySQL deployments, including mixed-language text, private/deleted links and legacy URL base paths. Enforce restore and permission-review before making imported boards public.

## Version 1.1.2 — XenForo 2.2/2.3 source compatibility

The importer now performs an actual **read-only** table/column preflight before creating target import jobs or backups. This covers the fields read for users, nodes, threads, posts, attachments, polls, watches, profiles, and reactions. Missing required tables or columns fail with the source table and field named; no partial import proceeds. It validates the operator-supplied version against the available attachment key format, not against a guessed version number. A XenForo 2.3 snapshot must contain `attachment_data.file_key`. XenForo 2.2 accepts `file_hash` and mixed upgraded schemas; where both columns exist on a 2.2 source, the stable key is preferred and empty keys fall back to the hash. For 2.3, a missing or malformed key must not be substituted with the legacy hash. An invalid or absent per-row key does not produce an arbitrary file path.

New jobs record `source_schema_sha256` and `source_attachment_key` in the existing `plan_json`. On continuation, a changed table layout or attachment key causes a fail-closed refusal. **Jobs created with 1.1.1 still resume using their original ledger**, without injecting new fields or changing phase indices; their earlier schema integrity guarantee is limited to the existing snapshot counts/tree hash. Do not manually edit `plan_json` or reuse a snapshot label after changing source data. File copies must remain a frozen local `internal_data/attachments/` tree; remote Flysystem-backed media is not fetched by this importer and must be staged separately. Source password hashes, private messages, ACL grants and other unsupported entities remain excluded.

Run `php tools/forum-xenforo-schema-unit.php` on any PHP 8.4 host and `php tools/forum-xenforo-schema-regression.php` with PDO SQLite; CI runs both. Before any production migration, also test against immutable **real** XenForo 2.2/2.3 database and attachment snapshots in staging and inspect the preflight and skipped-file report. This release does not claim certification against every add-on schema.

## Version 1.1.1 — resumable additional XenForo import phases

New XenForo import jobs record `pipeline_version=2` in `ce_forum_import_jobs.plan_json`. This changes **neither** the existing database layout nor the original indices in `ForumSource::PHASES`. New jobs process the original eleven phases, then `profiles`, then `reactions`; existing jobs whose plan has no pipeline marker continue and finish after the original eleven phases, including if resumed using 1.1.1. Never manually modify the phase or pipeline marker of a running job.

XenForo 2.2/2.3 additional phases read `xf_user_profile` and `xf_reaction_content` from the same read-only source snapshot. Use `forum:import:plan` to check that required columns are present and review `profiles`/`reactions` counts **before** creating a backup or running the import. The adapter rejects an unsupported source layout. If tables come from a custom fork, restore a verified snapshot and use a compatible copy; do not disable preflight. MyBB, SMF and phpBB remain on the historical phase sequence; their additional data will be added in later releases.

Imported profile fields are created only for newly imported users and remain **private**, with no automatic activation of account or public profile. Oversized or malformed fields, unsafe profile URLs and missing users are explicitly skipped. Only standard XenForo Like and Love reactions are currently mapped to target `like` and `celebrate`; custom, negative, self reactions and records referring to excluded users or messages are tracked as skipped with distinct reasons. Additional data, its ID map, and the job checkpoint are committed together; restarting a failed batch is idempotent. When `state=complete`, inspect `results` in `forum:import:status` and reconcile the skips before making a migrated community visible.

This release does **not** yet migrate private conversations, all reaction semantics, profile images or profile custom fields. These are subsequent roadmap stages, and a production cutover requires staging validation with actual XenForo snapshots and the target PostgreSQL/MySQL storage.

# Forum Migration Engine — phpBB 3.3 (0.7.5)

The importer is an operator-only CLI, not the CMS Portable ZIP importer. It accepts a **frozen copy** of a phpBB 3.3 database in MySQL/MariaDB or a SQLite copy with the same tables. Keep the source DB and attachment directory immutable for the whole import. Do not point it at the live forum. Use a dedicated SELECT-only source database account; the adapter also sets read-only transaction mode. The SQLite source is opened with `query_only`. Source credentials are provided in environment variables, never saved to the target or passed on the command line.

## Preparation and execution

1. Upgrade the target to 0.8.0, run `php bin/cajeer migrate`, configure backup keys (`php bin/cajeer backup:keygen --key=/secure/backup.key` as documented), and verify a backup/restore drill. Stop all target PHP/queue/scheduler processes on **every** node and enter operator maintenance. Do not run other writers or deployments during import. Use a staging installation first.
2. Freeze phpBB database and `files/` directory, use a stable snapshot label. Set `FORUM_IMPORT_SOURCE_DSN='mysql:host=127.0.0.1;dbname=phpbb_snapshot;charset=utf8mb4'`, `FORUM_IMPORT_SOURCE_USER`, `FORUM_IMPORT_SOURCE_PASSWORD` securely in the process environment. Alternatively `FORUM_IMPORT_SOURCE_DSN='sqlite:/absolute/path/source.sqlite'`. Never store credentials in Git or shell history. Source database and target database must be distinct.
3. Plan (no target writes):

```sh
php bin/cajeer forum:import:plan --snapshot=community-2026-11 --prefix=phpbb_ --files=/srv/phpbb-snapshot/files --json
```

4. Inspect source counts and unsupported entities. Use exactly the same DSN, snapshot label, prefix and files directory on every run. The job ID is the hash of these source identifiers and source version; it is **not** a content checksum. Do not change these parameters to resume. If source data changes, restore target backup and start again with a new immutable snapshot. The final check compares counts/high-water marks, but cannot detect edits preserving those values.

```sh
php bin/cajeer maintenance:on
php bin/cajeer forum:import:run --snapshot=community-2026-11 --prefix=phpbb_ --files=/srv/phpbb-snapshot/files --confirm=import-phpbb --batch=100 --steps=50 --json
```

The first run captures and verifies a complete recovery backup through the existing BackupManager before any import writes. Each batch commits data, ID map and checkpoint together. On a process failure or uncertain commit rerun exactly the same command; the committed checkpoint determines the next batch. `--steps=1` is the default; use a bounded number of steps or repeat in an operator script. `--batch=1..500`, posts capped at 20, attachments one at a time, watches/votes paginated by source user. Status and ID mapping need no source credentials:

```sh
php bin/cajeer forum:import:status --job=JOB_ID --json
php bin/cajeer forum:import:map --job=JOB_ID --kind=topics --id=123 --json
```

Wait for `job.state=complete`. `results` counts mapped/skipped source entities by reason; `relation_rows` counts actual imported vote/watch rows. For watches and votes the map is per parent, not per individual membership; compare relation counts with source totals. Keep the job and backup IDs. A successful CLI exit means the requested batch ran, not necessarily that the import is complete.

## Review and cutover

- The new root category and every imported board are **hidden**, readonly and SEO-disabled. No automatic ACL translation. Review source ACLs and create appropriate target group/user rules through ACP before opening any board. Set parent and child visibility, read/write permissions, SEO, and state deliberately. Keep confidential boards hidden. The original site tree and accounts are not merged or replaced.
- Every new account is disabled, with a random replacement password hash, private profile/activity, no verified email, and only normal `forum-member` plus non-privileged imported groups. Do not activate source banned/inactive accounts without manual review; source bans are not translated. For approved accounts activate through ACP, use existing password reset and email verification. Source founders/admins receive no special rights. Existing email collisions are skipped, not linked; authors without a mapped account become anonymous/null. Never change existing account credentials to resolve a collision.
- Review the report: unapproved/deleted/moved topics, unapproved posts, links, unknown parents, empty topics, invalid emails, unsupported attachments and private messages are not imported. phpBB s9e XML/legacy BBCode is converted to literal text, not arbitrary HTML; formatting and embedded media/quote links may require manual repair. Post order follows source post IDs; timestamps retained (account timestamps are limited to MySQL TIMESTAMP range). Source polls are closed; compatible registered votes and internal subscriptions are imported. Guest votes, private messages, ACL rules, bans, custom profiles, remote media, avatars and source credentials are not imported.
- Attachment source directory must be a frozen trusted local copy. Files use the existing type/size/MIME allowlist, validated paths relative to the source root, SHA-256 and base64 private storage. Missing/unsafe/unsupported files and files exceeding post limits are reported. The importer does not copy private-message or orphan files. Large imports require sufficient database/disk space and appropriate MySQL `max_allowed_packet` (base64 adds overhead).
- The importer uses target FTS triggers, revisions, sequences, media state and cache generation triggers. It does not enqueue historical mail, notification or extension publication events. No separate counter rebuild is required for dynamic counters. At completion the target integrity check must pass. Run `php bin/cajeer forum:search:check --json` and `forum:performance:check --json` after leaving maintenance in the isolated installation; check search/SSR/sitemap visibility, attachment downloads, and test opening a permitted board. Keep target hidden from public traffic until checks pass.
- Legacy ID map is available for future redirect integration. No automatic public redirects from phpBB URLs yet. If aborting, use `php bin/cajeer backup:restore --id=... --yes` with the saved backup ID (consult `backup:restore` CLI help for operator confirmation); this restores the full target recovery set, not just imported rows. Do not resume unrelated writes before restore. After review, leave maintenance and restart workers.

## Testing and limits

`php tools/forum-migration-regression.php` exercises the actual importer on a disposable SQLite target and a synthetic phpBB-compatible snapshot, including failure/resume, hidden content, email collision, attachments and votes. `python tools/forum-tests/migration_sql_regression.py` exercises the exact target SQL on SQLite. Real phpBB MySQL/MariaDB dumps and PostgreSQL/MySQL targets must be tested in staging before production cutover. Online delta migration, automatic ACL equivalence and large-scale performance certification are not implemented. The multi-forum ACP monitor is described below; execution remains operator-only.

## Multi-forum sources (0.7.6)

The same import ledger and transaction engine now reads XenForo, MyBB and SMF directly. No new target schema is required beyond 0047. Existing phpBB commands and jobs retain their original identity and checkpoint format.

| `--platform` | Source family / schema | Default prefix | Local attachment root (`--files`) |
|---|---|---|---|
| `phpbb` (default) | 3.3.x (auto-detected) | `phpbb_` | Original `files/` |
| `xenforo` | 2.2.x or 2.3.x | `xf_` | Original `internal_data/attachments/` |
| `mybb` | 1.8.x | `mybb_` | Original `uploads/` |
| `smf` | 2.1.x | `smf_` | Staged numbered subdirectories, one per `id_folder` |

For non-phpBB sources specify the actual installed version, e.g. `--source-version=2.3.0`. The adapter validates the supported family and the required native tables/columns before taking a target backup. SMF additionally checks `smfVersion` when present. No promise is made that all patch releases, modified schemas or plugins are compatible. Test an actual frozen source in staging. Sources can be MySQL/MariaDB snapshots or SQLite copies with native table layouts (not SQL dumps passed directly as DSNs).

Example for XenForo:

```sh
# Set FORUM_IMPORT_SOURCE_DSN, FORUM_IMPORT_SOURCE_USER and FORUM_IMPORT_SOURCE_PASSWORD securely first.
php bin/cajeer forum:import:plan --platform=xenforo --source-version=2.3.0 --snapshot=xf-frozen-01 --files=/srv/xf/internal_data/attachments --json
# Stop all application nodes and workers, enter maintenance, then:
php bin/cajeer forum:import:run --platform=xenforo --source-version=2.3.0 --snapshot=xf-frozen-01 --files=/srv/xf/internal_data/attachments --confirm=import-xenforo --batch=100 --steps=50 --json
```

Use `--platform=mybb --source-version=1.8.39 --confirm=import-mybb` or `--platform=smf --source-version=2.1.6 --confirm=import-smf` for the corresponding source (omit `--confirm` for plan). Override `--prefix` as necessary. Keep the exact same platform/version/prefix/DSN/snapshot label/file root between resumptions. Changing any creates a distinct job; do not use a new label to restart an incomplete import. Restore its backup if the source snapshot has changed. New jobs compare the normalized node tree digest and source counts/high-water marks on resume and completion. This is not a full-content cryptographic snapshot guarantee.

New sources transfer native users and ordinary group memberships (including numeric user ID 1), nested categories/boards, visible topics/posts, closed/locked/pinned metadata, post revisions, local post attachments, closed polls and compatible registered votes, topic and board subscriptions. Posts are imported as literal text; source BBCode, media embed tags and internal links are not fully rewritten. Source-specific system roles are not granted. All new users remain disabled and all imported boards hidden/readonly/noindex until reviewed. Email collisions are skipped. Source private messages, sessions, credentials, reactions, reputation, avatars, sanctions, custom fields, automatic ACL translation are not imported; source counts are reported for the applicable major unsupported tables. Guest votes are skipped. No historical notification or extension events are emitted.

Attachment handling:

- XenForo: original file at `<floor(data_id/1000)>/<data_id>-<key>.data`. XF 2.3 uses `file_key`; older schema with no such column uses `file_hash`. Only associated post attachments and valid matching post authors are imported. Do not use thumbnail directories or remote storage URLs.
- MyBB: `attachname` is a path relative to `uploads/`, often `YYYYMM/post_...attach`. Unapproved, orphan and unsafe paths are skipped.
- SMF: stage immutable original files into numbered folders, e.g. `1/40_<file_hash>` under the specified root for attachment 40 and folder 1. Legacy unhashed files, avatars, thumbnails and unapproved files are not imported. The adapter does not read arbitrary original server paths from database settings. SMF category mappings use synthetic source ID `4294967296 + id_cat`, while original board IDs remain unchanged; `kind=forums` can inspect both. SMF recycle-board topics are excluded when the recycle setting is enabled.

The importer verifies the target file allowlist, source length, canonical path containment, SHA-256 and attachment ownership; no arbitrary path traversal or symlink escape. It deliberately uses bounded per-file memory (up to 25 MiB) and SQL base64 storage, not a new blob storage backend. Node trees are bounded to 100,000 nodes and target depth 16; malformed, cyclic or orphan trees fail preflight. Source data remains untouched.

## 0.7.7 — bounded import and recovery

Use `--seconds=60 --steps=1000 --progress-only=1` on `forum:import:run` to stop between committed batches after a soft time budget. The first backup, source planning and final integrity checks are not bounded by this timer. The default full report remains compatible; progress-only avoids re-scanning the entire ledger and relation tables until completion. `forum:import:status` still returns the full report. Use the same immutable snapshot parameters each time.

Only one unfinished migration is permitted. `maintenance:off` refuses to reopen an installed forum until the job completes or its pre-import backup is restored. Keep all nodes/workers drained, including remote nodes sharing the DB. Resume reads the durable checkpoint and never retries an uncertain SQL commit automatically. A failed source attachment read aborts the batch; fix storage access before resuming. Missing or unsupported source files are still explicitly skipped. `--verify-backup=1` verifies the complete authenticated recovery set before a run; otherwise its manifest must exist and the set must not have an incomplete marker. Verify before resuming after storage failures. Do not delete the recovery set until cutover is accepted.

```bash
php bin/cajeer backup:verify --id=BACKUP_ID --json
php bin/cajeer forum:import:status --job=JOB_ID --json
# On unrecoverable failure, restore the verified pre-import set under maintenance:
php bin/cajeer backup:restore --id=BACKUP_ID --yes
```

Restore is whole-installation recovery, not a partial undo. It restores the prior code and database together and may restore an older edition; use a fresh backup for each independent job. On multi-node installations coordinate maintenance and cache namespace across every replica. After a full restore, change `FORUM_REDIS_NAMESPACE` before allowing traffic to prevent reuse of keys from a discarded database state.

Finalization validates that each imported primary mapping still resolves, verifies the search indexes and active theme, and runs the forum integrity check. Before starting or resuming, the CLI validates the active forum design and enabled extension dependency graph, signatures and compatibility using the existing extension registry. It does not execute providers or emit historical publication events. After import, test installed plugins and the active theme on staging; `extension:runtime:boot --json` and the existing signed package workflow remain the operator's tools.

### Old links

The job-scoped HTTP resolver is intentionally explicit to avoid collisions when several source forums reuse numeric IDs. For a completed job with reviewed public ACLs:

- `/forum/legacy/JOB_ID/topics/15432` → current topic
- `/forum/legacy/JOB_ID/posts/89210` → current topic page and post anchor
- `/forum/legacy/JOB_ID/forums/15` → current board
- `/forum/legacy/JOB_ID/url/viewtopic.php?t=15432` (phpBB)
- `/forum/legacy/JOB_ID/url/showthread.php?tid=15432` (MyBB)
- `/forum/legacy/JOB_ID/url/index.php?topic=15432.0` (SMF)
- `/forum/legacy/JOB_ID/url/threads/example.15432/` (XenForo)

For the old host, configure an **internal rewrite** to `/forum/legacy/JOB_ID/url/<old-path>` preserving the query string; replace JOB_ID with the actual 64-character job ID. For example, on a dedicated phpBB legacy host, with the same PHP front controller and public root:

```nginx
location = /viewtopic.php {
    rewrite ^ /forum/legacy/JOB_ID/url/viewtopic.php last;
}
location = /viewforum.php {
    rewrite ^ /forum/legacy/JOB_ID/url/viewforum.php last;
}
```

Use an equivalent route for the other source platforms; do not blindly rewrite a shared site's `index.php`. The application selects the parser by the stored source platform, resolves the ID in that job and returns 301 only for currently guest-readable, live content. A private/hidden, deleted, skipped, unknown or incomplete mapping returns 404 with no Location. No query-provided host or arbitrary redirect destination is accepted. The response is `private, no-store` and `noindex` to avoid reusing stale ACL decisions. Old page offsets are not mapped unless a post ID is present; canonical topic URLs remain unchanged. The original domain must be routed to the new installation or reverse-proxied by the operator.

### Larger regression

`php tools/forum-migration-reliability-regression.php --topics=1200` creates a synthetic XenForo snapshot and imports real topics, posts and subscriptions into a disposable target, injects a relation-write failure, resumes from a partial watcher checkpoint, verifies the full-text index, activates a real theme and boots the existing template plugin. It also checks public legacy links and ACL revocation. CI executes it with PDO SQLite. To increase size use `--topics=10000` (or up to 100000); run on a staging host with sufficient disk space. It prints measured batch counts, runtime and peak PHP memory, not a production throughput guarantee. The existing per-file 25 MiB bound and SQL base64 representation still apply; importing 100 GB of attachments requires appropriate database/dump/disk capacity and a real recovery drill.
