# Обновление Forum Edition до 1.6.0

[Документация](README.md) / Обновления

## Совместимость и допуск

Целевой выпуск — Forum Edition `1.6.0`, минимальный подписанный источник — `1.5.11`. Более ранние установки обновляйте последовательно проверенными релизами. Новых миграций и runtime-зависимостей относительно 1.5.11 не добавлено. Уже применённые миграции не изменяйте. Не используйте изменённый ZIP как полноценный dist.

> [!CAUTION]
> Не запускайте обновление из предоставленного исходного архива до устранения расхождения идентичности сборки и получения прошедшего приёмку подписанного dist. Публикация без `Latest` всё равно делает релиз доступным клиентам GitHub. Если необходимо дождаться postpublication-приёмки, заранее заблокируйте или отложите версию 1.6.0.

## Подготовка

1. В отдельном staging воспроизведите текущую версию, настройки, расширения, выбранную БД и тип очереди.
2. Убедитесь в наличии исходного и целевого неизменяемых dist, доверенного ключа и актуальной подписанной авторизации. Не доверяйте ключу внутри скачанного пакета.
3. Проверьте состояние БД, историю миграций, свободное место, сервисы, права, внешние хранилища и доступность ключа резервного копирования. Подготовьте проверенную копию БД, файлов, `.env`, приватных медиа и отдельно внешних секретов.
4. Проверьте восстановление в изолированной среде. Автономный режим дополнительно требует фактического восстановления точного свежего snapshot до замены файлов.
5. Выберите окно обслуживания, организуйте остановку записи, согласуйте порядок восстановления и критерии открытия трафика.

## Выбор политики

| `UPDATE_POLICY_MODE` | Назначение |
| --- | --- |
| `legacy` | Совместимость с прежними флагами |
| `disabled` | Запрет новых операций обновления |
| `notify_only` | Обнаружение без автоматической подготовки |
| `download_only` | Автоматическая подготовка, без автономной установки |
| `manual_approval` | Подготовка с явным подтверждением установки |
| `automatic_security` | Автономный допуск подписанных security-релизов |
| `automatic_patch` | Только patch в стабильной ветке; не допускает 1.5.11 → 1.6.0 |
| `automatic_minor` | Stable patch/minor, допускает переход 1.5.11 → 1.6.0 |
| `fully_automatic` | Релизы разрешённого канала в пределах политики |

Автономный допуск требует отдельного разрешения хоста `UPDATE_AUTO_APPLY_ENABLED=true` и всех предусловий оператора; выбор режима сам по себе недостаточен. `UPDATE_AUTO_CHECK_ENABLED=false` отключает обнаружение, фоновую подготовку и автономную установку. Ручные действия остаются под собственными проверками и политикой. Политика, каналы, промежуточные версии, окно и блокировки перепроверяются перед изменением установки.

## Ручной контролируемый сценарий

Проверьте статус и подлинный dist через установленный CLI, а не через непроверенный новый код. Пример preflight для доверенного 1.5.11:

```bash
php bin/cajeer update:check --json
php bin/cajeer update:status --json
php bin/cajeer update:apply --package=/srv/releases/cajeerengine-1.6.0-dist.zip --version=1.6.0 --sha256=APPROVED_SHA256 --dry-run --json
```

Замените `APPROVED_SHA256` точным одобренным SHA-256; подпись и остальные sidecar-файлы должны быть доступны согласно действующей процедуре. Dry-run не выполняет миграции и не подтверждает успешную установку. После независимого допуска, подготовки копии и остановки записи оператор может выполнить ту же команду без `--dry-run`. Web ACP сам код не заменяет.

## Автономный сценарий (только поддерживаемый Linux-хост)

Для существующей установки с SQLite/PostgreSQL необходимы отдельный непривилегированный updater, действующий recovery supervisor, защищённая политика systemd/Polkit, доверие Ed25519, ключ бэкапа, совместимая очередь и хранилище, Nginx maintenance gate. MySQL/MariaDB, Redis-backed queue и внешнее хранилище не входят в локальный автономный протокол восстановления. Не включайте in-place updater в immutable-контейнере.

Настройте все предусловия по [preflight](forum-update-backup-preflight-1.5.6.md), [systemd](forum-safe-deployment-1.5.7.md), [supervisor](forum-crash-recovery-1.5.8.md) и [trust policy](forum-update-security-1.5.10.md). Только затем выбирайте разрешённый режим и окно. В ACP `/admin/#/updates` можно проверить каталог, staging, прогресс, состояние оператора, транзакции, историю, копии и откат. Делегирование редактирования политик — отдельная опция, отключённая по умолчанию; ключи и права ОС не делегируются.

## Контроль результата и восстановление

После обновления проверьте:

- точную версию и целостность управляемых файлов;
- `/health/live`, `/health/ready`, вход, темы и ответы, поиск, ACL, ранее созданные данные;
- запуск PHP-FPM, worker и scheduler, очередь и отсутствие дублирующего применения;
- журнал транзакции, состояние копии, историю и отсутствие незавершённого recovery.

```bash
php bin/cajeer update:status --json
php bin/cajeer update:history --limit=20 --json
```

При сбое не удаляйте marker-файлы, trust pins или журналы, не запускайте повторное обновление при неизвестном результате. Приостановите новые запуски, сохранив действующий процесс восстановления. Откат уже зафиксированного обновления может уничтожить новые записи после снимка и не отменяет внешние письма/webhook. Выбирайте точную зафиксированную транзакцию, а не только номер версии. Используйте [восстановление](forum-crash-recovery-1.5.8.md) и [secure update operations](secure-updates.md) с учётом текущей политики.
