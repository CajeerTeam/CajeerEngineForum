# CajeerEngine Forum 1.0.5 — Account Provisioning

Этот релиз добавляет реальную регистрацию новых пользователей форума через проверенный вход SkiF4er ID (Keycloak OIDC). Ядро CajeerEngine остаётся **2.1.0**. Новые SQL-миграции не нужны: используются `ce_users`, `ce_user_roles`, `ce_oidc_identities` и существующие таблицы политики/антиспама форума.

## Включение

1. Создайте резервную копию БД и файлов; установите изменённые файлы поверх полного **Forum 1.0.4** на тестовом стенде.
2. Примените существующие миграции проекта: `php bin/cajeer migrate`. Проверьте наличие `forum-member`, `ce_forum_community_settings`, `ce_forum_spam_lock` и схемы OIDC.
3. В `.env` настройте `APP_URL=https://ВАШ_ДОМЕН`, `SKIF4ER_ID_ENABLED=true`, `SKIF4ER_ID_CLIENT_ID`, `SKIF4ER_ID_CLIENT_SECRET`, стабильный секрет хранилища OIDC. В Keycloak зарегистрируйте точный `https://ВАШ_ДОМЕН/auth/oidc/callback` и включите Authorization Code + PKCE S256; см. https://id.skif4er.ru/sdk/.
4. После проверки входа уже привязанных пользователей включите **`SKIF4ER_ID_AUTO_PROVISION=true`**. При этом должны быть включены **`FORUM_REGISTRATION=true`** и **`registration_enabled=true`** в актуальной политике сообщества (Forum ACP).
5. На `/forum/register` появится кнопка «Создать аккаунт через SkiF4er ID». На callback пользователь с новым `(issuer, sub)` и **подтверждённым email** получает собственный UUID и единственную роль `forum-member`. Email считается подтверждённым благодаря валидированному ID token. Использование внешнего email для связи с существующим UUID **запрещено**.

## Реальное поведение

- Новый внешний пользователь: проверка токена у IdP → регистрационный лимит → блокировка регистрации и актуальная политика → отсутствие email/subject-дублей → запись пользователя + роли + подтверждённого email + идентичности в **одной транзакции** → создание локальной HttpOnly-сессии → `/forum/account?created=skif4er`.
- Повторный вход с тем же `(issuer, sub)`: возвращается ранее созданный UUID без создания второго пользователя или повторной выдачи роли.
- Уже имеющийся локальный email: регистрация отклоняется; пользователь должен войти локально и выполнить безопасную привязку в `/forum/account/security`.
- Регистрация закрыта глобально или в ACP: **новые** SSO-аккаунты не создаются; уже привязанные пользователи могут входить.
- SSO-only профиль не может отвязать единственный внешний метод входа до отдельной реализации безопасного локального способа входа.
- Неисправный/избыточно привилегированный `forum-member`: регистрация отказывается выдавать права.

## Приёмка перед production

На CI запустите `php tools/forum-account-provisioning-regression.php --require-db`, `php tools/oidc-regression.php`, `php tools/forum-account-linking-regression.php` и штатные SQL/Forum регрессии. Требуются PHP 8.4, `pdo_sqlite`, `mbstring` и Composer-зависимости. Проверяйте также реальный OIDC вход, регистрацию, закрытую регистрацию, конфликт email, повторный вход, отзыв сессии и права на staging с PostgreSQL 17/18 и настоящим Keycloak. Локальный тест с SQLite не является доказательством production-сертификации.

**Важное:** конфигурация `SKIF4ER_ID_AUTO_PROVISION` по умолчанию выключена. Не включайте её до настройки точных Keycloak redirect URI, HTTPS, надёжных ключей и антиспам-ограничений. Не сохраняйте client secret или ID token в публичном коде либо браузерном localStorage.
