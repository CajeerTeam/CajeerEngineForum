# CajeerEngine Forum 1.1.0 — SkiF4er ID Stable

Выпуск Forum Edition **1.1.0**, ядро **CajeerEngine 2.1.0**. Рабочие серверные сценарии входа, привязки, регистрации, сессий, выхода, ACL и MFA наследуются от 1.0.3–1.0.9. Новых SQL-миграций **нет**; изменения касаются проверок и обязательной процедуры выпуска. Не считайте исходный ZIP патчем, уже прошедшим production admission.

## Условия запуска

Перед изменением системы: сохраните проверенную резервную копию файлов и БД с отдельной копией `.env` и ключей, проверьте восстановление на изолированной площадке. Обновите исходники, выполните `composer install --no-dev`, перезагрузите все PHP-FPM workers, затем (в отдельное окно технического обслуживания):

```bash
php bin/cajeer migrate
php bin/cajeer identity:sessions:status
# При необходимости выполнить backfill на резервной/тестовой копии:
php bin/cajeer identity:sessions:migrate --yes --batch-size=100 --max-batches=10
php bin/cajeer identity:acceptance --require-oidc --probe-idp --probe-site
php tools/forum-security-acceptance.php --json
```

Последняя команда **ничего не записывает**, но требует настоящую БД, зарегистрированный confidential OIDC-клиент, `SKIF4ER_ID_ENABLED=true`, рабочую HTTPS-площадку, доступные discovery/JWKS, установленный `vendor` и свежие workers. `--offline` предназначен только для тестового окружения и не является доказательством production readiness. `IDENTITY_SESSION_STRICT=true` включайте только после завершения переноса legacy-сессий и rolling restart. Не публикуйте выводы с секретами.

Новый HTTP probe проверяет реальную страницу `/forum/login` без cookies, следования редиректам, обхода TLS или кеширования. Ответ 200 должен содержать `X-CajeerEngine-Forum-Version: 1.1.0`, HTML и `/forum-assets/forum.js?v=1.1.0`. Публичный identity status должен содержать заголовки **обеих версий** — ядра 2.1.0 и Forum Edition 1.1.0. Если сайт отдаёт старую версию, сначала обновите все runtime узлы и очистите CDN/кеш. Приёмка БД также отказывает при осиротевших OIDC-связях, неконсистентных SSO-сессиях и частично отозванных сессиях.

## Обязательная проверка с настоящим SkiF4er ID (на staging)

В отдельном браузере и отдельной тестовой учётной записи проверьте **каждый сценарий с реальными запросами и состоянием БД**:

1. Локальный вход остаётся доступным. Вход SkiF4er ID открывает `/forum`, не `/admin/`; возврат в тему сохраняется, чужие и внешние return URL отвергаются.
2. Локальный владелец привязывает собственный SkiF4er ID после свежего пароля/TOTP. Привязать тот же `(issuer,sub)` к второму аккаунту невозможно; email не служит основанием для автоматического слияния. Отвязка единственного метода входа запрещена.
3. При открытой регистрации новый подтверждённый внешний аккаунт получает только `forum-member`. При закрытой регистрации первый SSO-вход не создаёт профиль. Повторный вход использует прежний UUID, темы и сообщения.
4. После входа через обе схемы `/forum/account/sessions` показывает текущую и другие сессии. Отзыв конкретного устройства, всех других и всех сессий немедленно отказывает следующему защищённому запросу. API-токены не должны быть удалены вместе с браузерной сессией.
5. Локальный выход оставляет IdP авторизованным; глобальный выполняет RP-initiated logout. Проверенный Back-Channel Logout по `sid` или `sub` отзывает только соответствующие SSO-сессии, повторный `jti` не имеет эффекта.
6. Повышение прав/редактирование ACL/санкций требует свежего MFA того же пользователя и сессии. SSO-пользователь не может повысить assurance локальным паролем. После понижения прав новый защищённый запрос отвергается; блокировка пользователя не блокирует страницу выхода.
7. Восстановите из резервной копии ранее существовавшую схему форума; выполните все миграции на используемом драйвере БД, затем проверьте UUID, разделы, темы, сообщения, ACL, OIDC-связи, сессии и откат. Во время недоступности IdP запрещены новые неподтверждённые входы, но существующие локальные сессии проверяются локально.

Регистрация клиента: issuer `https://id.skif4er.ru/realms/skif4er`, confidential client, Authorization Code + PKCE S256, HTTPS redirect URI `<APP_URL>/auth/oidc/callback`, `post_logout_redirect_uri` на `/auth/oidc/logout/complete`, back-channel `/auth/oidc/backchannel-logout`. Секрет и ключи хранятся вне репозитория.

## Приёмка подписанного релиза

`forum-ci.yml` на защищённой ветке `main` теперь требует `FORUM_RELEASE_SIGNING_KEY_B64` и `FORUM_RELEASE_TRUSTED_PUBLIC_KEY_B64` (base64-encoded raw Ed25519 private/public key). PR и непубликуемые ветки используют временные ключи, но не допускаются к публикации. Секрет следует создать/хранить во внешней системе управления секретами; не фиксируйте его в Git.

`forum-release.yml` повторно проверяет доверенный public key, SHA-256/signature source/dist, сертификат привязки к точному Git SHA и все evidence CI/staging/host/DR до создания черновика. Публикация выполняется только через защищённое GitHub environment `forum-production`, в настройках которого **необходимо включить обязательное подтверждение независимыми ревьюерами**. Без включённых reviewers одних YAML-файлов недостаточно для организационного допуска.

Отдельные `forum-long-qualification.yml` и `forum-chaos-update.yml` требуют изолированного оборудования и настроенного trusted key; короткий CI **не заменяет** независимые 24-часовые нагрузки и аварийное восстановление. Публикация Github Release также не означает, что конкретная production-инсталляция прошла реальные OIDC browser E2E.

**Решение GO** допускается только после фактических зелёных CI, защищённого разрешения публикации, пройденного `forum-security-acceptance.php --json` на рабочей площадке, успешного IdP E2E и проверенного восстановления из резервной копии. При любом `failed_checks`, несоответствии версий, неверном ключе или незавершённой миграции — **NO-GO**. Не удаляйте миграционные failure-маркеры вручную и не перезаписывайте старые теги или релизы.
