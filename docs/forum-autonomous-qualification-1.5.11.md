# Forum Edition 1.5.11 — Automated Updates Qualification & RC

This release is a **candidate**, not proof of production certification. The protected publication workflow now requires five independent successful runs on the same main commit: full CI (including Chromium/Firefox live E2E, SQL and queue matrices), physical 10k/100k/1M with 24-hour soak, both interrupted signed Compose update checkpoints, and live GitHub autonomous host qualification. The latter uses the actual published 1.5.9 → 1.5.10 transition: an unpublished candidate cannot honestly be discovered by the production canonical public catalog. The candidate itself must pass exact signed dist CI, physical and SIGKILL recovery from the authentic published 1.5.10. The digest of the real GitHub-downloaded 1.5.10 must match both physical rollback baseline reports. No fixture transport or manual update is accepted as evidence of a live GitHub update.

## Dedicated physical host

Use a disposable, isolated Linux VM (never a production site), runner label `forum-autonomous-benchmark`, runner executing as the same non-root `cajeer-updater` UID. Checkout must be outside `/var/www/cajeerengine`. Install authentic 1.5.9 with real PHP-FPM, PostgreSQL or SQLite, Redis if configured, Nginx loopback TLS, worker and scheduler. Provision the service policy, host supervisor, backup key and publisher trust per 1.5.6–1.5.10 documentation. A signed, unexpired official 1.5.10 GitHub dist must exist and be the next eligible stable release. Use the same independent publisher public key as candidate CI (repository variable `CE_AUTONOMOUS_TRUSTED_PUB`, absolute root-owned file). The protected environment must require independent approval. Disable the operator timer and wait for the service to be inactive; the test invokes the actual independent supervisor with the same UID and required host environment. Set `BACKUP_KEY_FILE` in runner environment if needed; never store secrets in workflow reports. Configure `UPDATE_AUTO_APPLY_ENABLED=true`, `UPDATE_POLICY_MODE=automatic_patch`, `UPDATE_SEQUENTIAL=true`, `UPDATE_CHANNEL=stable`, web/operator enabled, full maintenance window for this isolated test only, no deferred release or blocklist. Do not use a simulated service runner. Restore a clean VM snapshot for each run.

Create `/etc/cajeerengine/qualification-fixture.json`, root-owned and not group/world-writable, with the following shape (replace actual local state/CA paths):

```json
{"purpose":"forum-autonomous-update-qualification","source":"1.5.9","target":"1.5.10","root":"/var/www/cajeerengine","domain":"forum.test","port":18443,"ca":"/etc/cajeerengine/qualification-ca.pem","state":"/var/lib/cajeerengine-qualification/smoke.json"}
```

Use a fixture containing a public thread and reply (`thread` and `reply` UUIDs) with `ContainerSmokeBody`, `ContainerSmokeMarker` and `ContainerSmokeReply`, as in `deploy/container/smoke.py`. No existing update attempts, staged packages, manual requests, maintenance or recovery markers. The fixture must be expendable; the script installs a real update. The benchmark verifies actual TLS API, SSR and search content before and after the update, two 60-second balanced read loads (10 target RPS, minimum 5, P95 ≤500 ms, errors ≤0.1% per route, no semantic errors), a concurrent public request probe during automatic staging/apply (only valid content or maintenance 503), committed host-policy journal, exact snapshot database restoration proof, fresh downloaded ZIP and official key identity, installed distribution integrity, and no repeat installation. Total staging and installation ≤900 seconds. It fails closed and does not synthesize a success receipt on failure. Restore a clean snapshot before retrying.

Dispatch `forum-autonomous-qualification.yml` on main with the successful candidate CI run ID. Supply its successful run ID as `autonomous_run` to `forum-release.yml`, along with the existing four required IDs. Reports are hashed and bound to repository, commit, run attempt and exact candidate digest. The publishing gate independently rejects missing evidence, wrong identities, short/weak load, mismatched historical baseline and failed proof. No publisher secret is included in the change ZIP.

Local validator tests: `python3 tools/forum-tests/test_autonomous_qualification.py`; full CI and the physical workflows are separate, mandatory operations. No database migrations or new application dependencies.

## After publication: exact candidate through GitHub

Reset the disposable VM to authentic 1.5.10 (fresh update state), set the fixture `source` to `1.5.10` and `target` to `1.5.11`, then dispatch the same workflow with `phase=postpublication`. This verifies the real public GitHub upgrade to 1.5.11 and requires the downloaded dist SHA-256 to equal the exact independently verified candidate artifact. The report is deliberately separate and cannot satisfy the prepublication gate. Run while release authorization is still valid.
