# Forum Edition 1.5.6 — Automatic Backup & Preflight

Autonomous updates remain opt-in. In addition to the existing signed package, compatibility, migration history and application health checks, the operator checks capacity on the backup filesystem and SQLite restore destination, ownership and writable directories for deployment and rollback, availability of the recovery key and original environment, and database recovery prerequisites. A fresh backup is captured under the exclusive operation lease and maintenance gate. Before replacing any live files, the exact authenticated snapshot is restored into a private rehearsal workspace, files and environment are read back, and the database is restored and inspected. The manifest digest and recovery evidence are persisted in the update transaction journal and successful update report. The maintenance policy is checked again before activation; if the window has closed, the installation is deferred without replacing the live release.

- SQLite: actual isolated database copy with integrity and foreign-key checks and table reads. PDO SQLite or the configured independent Python interpreter is required.
- PostgreSQL: actual restore into a randomly named temporary database on the configured server; database owner, CREATEDB, pg_dump/pg_restore/createdb/dropdb and psql are required. Ensure the database server has capacity for an additional database; the actual drill must succeed. The drill does not boot the application and does not reproduce all ownership/ACL semantics of the live database.
- MySQL/MariaDB: autonomous application fails closed because an isolated restore implementation is not available. Manual updates retain their previous recovery prerequisites. External storage and Redis-backed queues remain unsupported by the local recovery protocol.
- The dedicated Linux operator must be able to preserve ownership and group of the recovery inventory. Use an installation layout owned by that operator, with service permissions arranged as documented for the host. Do not run the operator as root.

Optional off-site protection: set `UPDATE_BACKUP_OFFSITE_POLICY_FILE=/etc/cajeerengine/update-backup-policy.json` to a private external BackupPolicy JSON file (see `deploy/backup-policy.example.json`). Use a separate namespace for update snapshots, preferably on a separate device or an S3 destination. An encrypted recovery bundle is published and read back with its exact digest before autonomous installation. A configured destination failure prevents activation. These update recovery sets are not part of scheduled backup retention; retain and remove them explicitly after qualification. Keep the recovery key and any external secret files independently backed up; external secret files are not captured by the snapshot. Without an off-site policy only local proof is mandatory.

Rehearsal artifacts are private and removed on normal completion or caught failure. A hard kill can leave a private `rehearsal-*` directory or a temporary PostgreSQL `ce_dr_*` database. After confirming no operation or child process is active, review and remove only the orphan belonging to that failed attempt. Run the existing recovery command if the update journal remains active. The `verifying_backup` journal state precedes live file replacement and must not trigger a destructive restore. A failed rehearsal is not retried as an unbounded autonomous installation.

Run `php tools/update-backup-preflight-regression.php` in a disposable environment. This tests real SQLite restoration, exact off-site encrypted readback, tampering and fail-closed conditions. Full signed dist update, PostgreSQL restore and physical qualification require external CI/staging. A successful proof is not an application boot test, disaster recovery certification or a promise of zero downtime.

`VERSION` is the upstream engine version (2.1.0); `release.json` contains Forum Edition 1.5.6. The supplied 1.5.5 source had an inconsistent upstream VERSION file; an installed 1.5.5 instance with that defect requires manual repair/patch before the updater can identify it. Do not rewrite a historical signed release or bypass verification to compensate.
